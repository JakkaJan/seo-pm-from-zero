## Описание

SSHM автоматически сканирует сайты 8 клиентов студии, рассчитывает SEO-score (0–100), расставляет приоритеты P0–P3 и выдаёт:
- цветной консольный отчёт (Rich)
- CSV-файл для Excel
- алерты при обнаружении критических проблем
- delta-сравнение с предыдущим аудитом

## Быстрый старт

### 1. Клонировать репозиторий

```bash
git clone https://github.com/<your-username>/seo-health-monitor.git
cd seo-health-monitor
```

### 2. Создать виртуальное окружение и установить зависимости

```bash
python -m venv .venv
source .venv/bin/activate        # Linux / macOS
# .venv\Scripts\activate.bat     # Windows

pip install -r requirements.txt
```

**Требования:** Python 3.10+

### 3. Запустить аудит

```bash
python main.py
```

Что произойдёт:
1. Сканируются все 8 сайтов из `data/clients.csv`
2. Результаты сохраняются в `data/monitor.db` (SQLite, создаётся автоматически)
3. В консоли — цветная таблица с метриками и алерты
4. CSV-отчёт сохраняется в `reports/audit_report.csv`
5. Лог записывается в `logs/audit.log`

## Конфигурация

Все пороги и пути задаются в `config.yaml` — **без правки кода**:

```yaml
thresholds:
  ttfb_warning_ms: 3000       # Алерт, если TTFB > 3000 мс
  score_critical: 50          # Красная зона
  score_warning: 70           # Жёлтая зона
  broken_links_critical: 3    # Алерт при >= 3 битых ссылках
  score_drop_alert: 10        # Алерт при падении score > 10 пунктов
  title_optimal_min: 30       # Оптимальная длина title (мин.)
  title_optimal_max: 60       # Оптимальная длина title (макс.)
  description_optimal_min: 120
  description_optimal_max: 160

scanner:
  timeout: 10                 # Таймаут HTTP-запроса (сек)
  max_links_to_check: 20      # Максимум ссылок для проверки на битость
  user_agent: "Mozilla/5.0 (compatible; DELTA-SEO-Bot/1.0)"
```

| T7 | Тесты pytest (28 тестов) | 3 | 0.6 | **3.6** |

| **Итого** | | **21** | **4.2** | **25.2** |

**Дедлайн MVP: ~25 часов ≈ 3 рабочих дня** при 8-часовом рабочем дне.

**Обоснование buffer 20%:**
Buffer закрывает типичные MVP-риски: неожиданная блокировка сайтов по robots.txt/Cloudflare (R-001), несовместимость версий библиотек, время на code review и исправление edge-case при реальном сканировании живых сайтов. 20% — стандартная прибавка для задач с внешними HTTP-зависимостями, где реальная среда всегда отличается от локальных мок-тестов.

## Ответы на вопросы PM

### 1. Какие риски из Risk Register реализовались? Как вы их митигировали?

| Риск | Реализовался? | Митигация |
|------|--------------|-----------|
| **R-001** Блокировка robots.txt / Cloudflare | **Да, частично.** Несколько сайтов возвращали 403/503 при первом запросе. | Используем корректный `User-Agent: DELTA-SEO-Bot/1.0`, в config.yaml флаг `respect_robots: false`. При статусе ≠ 200 фиксируем `status_code` и продолжаем следующий клиент, не падая. |
| **R-002** Долгое сканирование (>30 сек) | **Да.** Сайты с большим числом ссылок. | `max_links_to_check: 20` в config.yaml ограничивает глубину. Каждый HEAD-запрос с `timeout=10`. |
| **R-007** Задержка из-за нехватки времени | **Управляем.** | Декомпозиция на 8 задач по 2–4 ч, buffer 20%, чёткие Definition of Done по каждой задаче. |

Риски R-003, R-004, R-005, R-006 — на стадии MVP не реализовались: это организационные и бизнес-риски, которые проявятся при внедрении в production.

### 2. Как интегрировать SSHM с Bitrix24 (CRM студии)?

**Схема интеграции (3 этапа):**

**Этап 1 — Webhook (Release 1.2, ~1 неделя)**
После каждого аудита `main.py` отправляет POST-запрос на Bitrix24 Webhook:
- Создаёт задачу на аккаунт-менеджера клиента при P0/P1
- Поле `DESCRIPTION` — автогенерированный текст с алертами
- Поле `DEADLINE` — +3 дня для P0, +7 дней для P1

```python
# notifier.py — добавить
import requests
def send_to_bitrix(webhook_url, client, alerts):
    payload = {
        "fields": {
            "TITLE": f"SEO Алерт: {client['client_name']}",
            "RESPONSIBLE_ID": client["bitrix_manager_id"],
            "DESCRIPTION": "\n".join(alerts),
        }
    }
    requests.post(f"{webhook_url}/tasks.task.add.json", json=payload)
```

**Этап 2 — Дашборд в CRM (Release 1.2)**
Bitrix24 поддерживает встроенные iframe-виджеты. SSHM экспортирует JSON API (`/api/audits`) → виджет в карточке клиента показывает последний SEO-score с динамикой.

**Этап 3 — Автоматизация через CRM роботы (Release 2.0)**
Bitrix24 CRM роботы запускают `main.py` по триггеру (смена стадии сделки, дата контракта) через REST API + cron на сервере студии.

### 3. Функционал для Release 1.1

| Фича | Приоритет | Обоснование |
|------|-----------|-------------|
| **Полный краулинг сайта** (2+ уровня вложенности) | Must Have | MVP проверяет только главную страницу — у крупных клиентов (ТЦ МегаМолл, 320 страниц) это слепое пятно. Реализуем через `asyncio + aiohttp` для скорости. |
| **PDF-отчёт** для клиента | Must Have | Аккаунт-менеджеры сейчас рассылают отчёты вручную. PDF с логотипом DELTA — часть клиентского опыта и аргумент ценности «Премиум» пакета. |
| **Email-уведомления** (SMTP) | Should Have | Consol-алерты в MVP видит только тот, кто запускает скрипт. SMTP-интеграция замыкает петлю: аккаунт-менеджер получает письмо автоматически. |
| **Scheduler (cron/APScheduler)** | Should Have | Ежемесячный запуск без ручного вмешательства — ключевое условие достижения метрики «100% охват клиентов». |
| **Веб-дашборд (FastAPI + простой HTML)** | Could Have | Внутренний инструмент для SEO-отдела: просматривать историю, фильтровать по менеджеру, сортировать по score. |

**Приоритизация по impact/effort:**
Краулинг и scheduler дают наибольший бизнес-эффект (охват клиентов, автоматизация) при умеренных затратах. PDF и email напрямую влияют на retention клиентов — ключевую OKR-метрику (78% → 90%).
